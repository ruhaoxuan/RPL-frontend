# 数据源同步与更新检查

## 页面与操作

首页在名称下方、来源饼图上方显示最近成功同步摘要。点击“查看数据源”进入数据说明页的“数据源与同步状态”，查看各来源的同步、版本和检查结果。多个来源的摘要标明最近成功的来源，不表示所有来源均已更新。Clippy、CodeQL、CVE、UB 是 RPL 内的分类，不是四个独立数据源。

页面每个来源只提供一个“手动同步”按钮。自动检查由本地后台调度，不提供独立的手动检查按钮。纯静态站点仅展示记录，需要另外接入经过认证的后端才能运行任务。

## 共用流程

所有入口都调用 `scripts/sync/workflow.ts` 中的 `runSource`。同一来源始终复用同一个检查实现。

```text
自动调度 / 命令行检查
  → 公共流程获取锁
  → adapter.check()
  → 保存检查记录、刷新检查栏
  → 释放锁

手动同步 / 命令行同步
  → 公共流程获取锁
  → 同一个 adapter.check()
  → 保存检查记录、刷新检查栏
  → adapter.pull(本次检查结果)
  → 校验候选快照
  → 激活来源版本、保存展示数据
  → 保存同步结果，检查栏改为“已是最新”
  → 清理并释放锁
```

检查失败时不调用拉取。检查成功、后续失败时保留本次检查信息及旧展示数据、成功时间。只有公共流程管理时间、状态和发布回退；来源脚本不自行保存同步记录。

没有新版本时，手动同步仍会执行拉取准备与校验；成功后刷新成功同步时间，表示现有数据在本次操作中再次通过验证。

## 时间定义和存储

`metadata/data-sources.json` 保存每个来源的配置与记录，随仓库提交。普通构建读取记录，不修改时间。前端使用 UTC ISO 8601 字符串，按浏览器时区显示。

| 名称                                 | 定义与更新时机                                                   |
| ------------------------------------ | ---------------------------------------------------------------- |
| 最近成功同步 `lastSyncedAt`          | 候选数据拉取、校验、保存成功时更新；不代表站点已发布或执行了检测 |
| 最近同步尝试 `lastSyncAttemptAt`     | 手动或命令行同步完成、失败时更新；自动检查不修改                 |
| 最近检查 `updateCheck.lastCheckedAt` | 共用检查阶段查询成功或失败时更新，手动同步也会更新               |
| 文件更新时间 `updatedAt`             | 上游最后一次修改对应文件的 Git 提交时间                          |
| 展示数据生成时间 `generatedAt`       | 生成目录数据的时间；普通启动和构建可能改变                       |

原来的顶层 `lastCheckedAt` 是同步尝试时间，已改名为 `lastSyncAttemptAt` 并保留原值。没有可靠历史记录时显示“尚未记录”，不补填日期。

检查记录还包含：开关 `enabled`、间隔 `intervalMinutes`、检查状态 `status`、远端版本 `latestVersion`、比较基准 `comparedVersion` 和失败摘要 `error`。检查结果是标注时间点的结论，成功同步后比较基准改为实际应用版本；不是对远端实时状态的保证。

## 每个数据源的两个实现

注册表为 `scripts/sync/adapters.ts`，接口定义为 `scripts/sync/types.ts`：

- `check(context)`：只查询版本，返回 `{ latestVersion, currentVersion }`。不写状态，不改变展示数据。
- `pull(context, checked)`：根据检查结果准备临时候选目录，返回 `PreparedSnapshot`。不直接发布目录或写时间。

`context` 提供仓库根目录、来源配置、临时工作区、候选输出目录、临时记录文件及日志回调。公共流程会准备候选记录供数据生成使用；其中的成功状态只存在于临时工作区，验证通过前不会作为正式同步成功记录发布。

`PreparedSnapshot.version` 必须等于检查所得版本。候选目录须包含完整的 `catalog.json` 和代码资源，保留其他来源的数据。公共流程执行目录结构及引用校验；来源可返回额外的 `validate()` 回调，检查内容资源和来源收录约束。存在外部版本切换时可返回 `activate()` / `rollback()`。适配器辅助 `cleanup()` 只负责清理临时来源文件，不承担业务状态保存。

目前 RPL 分为：

| 文件           | 职责                                                                        |
| -------------- | --------------------------------------------------------------------------- |
| `rpl-check.ts` | 用 `git ls-remote` 查询远端 master，与当前子模块 HEAD 比较                  |
| `rpl-pull.ts`  | fetch、准备固定版本 worktree、生成候选数据，提供额外校验和版本切换/恢复回调 |
| `workflow.ts`  | 两种任务共用的检查、状态保存、校验、发布、回退和锁                          |
| `service.ts`   | 来源路由、任务状态和定时调度                                                |
| `plugin.ts`    | 本机 HTTP 接口及最新展示资源读取                                            |

旧的 `rpl-git.ts` 整体同步脚本和单独的 `checks.ts` 编排已移除，避免两条流程重复维护检查结果。

RPL 拉取使用本次检查确定的提交，而不盲目使用之后变化的 master。若该提交无法获取，或检查后本地 HEAD 已变化，则拒绝发布并保留旧数据。固定 `metadata/allowed-pairs.json` 继续控制收录，新增上游模式不会自动收录。RPL 的额外校验继续检查源码哈希、对应表、代码资源和收录全集。

未来网页来源各自提供检查脚本和拉取脚本，并注册到相同接口。检查应提取稳定的版本标记或目标内容哈希，避免广告、访问量变化造成误报。拉取结果需转换为约定的候选目录格式，并提供必要的资源校验；仅增加元数据并不等于该来源可运行。浏览器或元数据不能指定任意 shell 命令。

## 成功与失败状态

| 场景                     | 检查栏                                               | 同步栏与展示数据                  |
| ------------------------ | ---------------------------------------------------- | --------------------------------- |
| 自动检查成功             | 已是最新／发现更新，刷新检查时间                     | 不变，不拉取代码                  |
| 自动检查失败             | 检查失败，刷新检查时间                               | 不变                              |
| 手动同步检查失败         | 检查失败                                             | 同步失败，不调用 pull，保留旧数据 |
| 检查成功，拉取或校验失败 | 保留已查询到的版本；版本不同则显示发现更新、尚未应用 | 同步失败，保留旧版本和成功时间    |
| 手动同步全部成功         | 已是最新，保留本次检查时间                           | 新数据与版本生效，刷新成功时间    |

若远端版本与当前相同，但收录校验失败，检查栏可以是“已是最新”，同步栏仍显示失败，两者含义不同。未取得任务锁或来源配置无效时，任务尚未开始，不伪造检查时间。

## 自动检查配置

本地 `npm run dev` 和 `npm run preview` 启动约 5 秒后检查到期来源，此后每 15 秒判断一次。默认间隔为 360 分钟。初次未检查视为到期；失败后按同一间隔再试。关闭服务后不再发起检查，重启按持久化时间判断是否补查。

配置在每个来源的 `updateCheck` 中：`enabled` 控制自动检查，`intervalMinutes` 最短为 1。关闭自动检查仍可手动同步。来源任务串行，检查与同步共用 `.data-sync/` 工作区锁，整个手动任务只取一次锁，不会在检查和拉取阶段重复取锁。

```sh
npm run dev
# 暂时关闭本进程自动检查，保留手动同步
RPL_AUTO_CHECK=0 npm run dev
# 独立检查，供维护或外部定时器使用
npm run data:updates -- rpl
# 完整同步：同一检查阶段 + 拉取、验证和保存
npm run data:sync -- rpl
```

同步不会自动提交、推送、部署或执行 RPL 检测。成功后提交记录、发生变化的子模块指针和核对后的元数据，再构建发布站点。

## 本机服务接口

| 接口                                | 用途                                         |
| ----------------------------------- | -------------------------------------------- |
| `GET /api/data-sources`             | 返回来源记录、能力、任务状态与忙碌状态       |
| `POST /api/data-sources/{id}/sync`  | 完整检查与同步任务                           |
| `POST /api/data-sources/{id}/check` | 只检查，供调度或维护使用，页面不单独提供按钮 |

POST 要求 `X-RPL-Sync: 1`。本机接口仅接受回环地址和同源访问。任务立即返回 202，前端轮询后刷新记录。完整技术日志留在终端，页面展示阶段摘要。任务状态在内存中，服务重启后不保留；时间、版本及失败记录保存在 JSON 中。同步状态响应在前端经过结构校验，异常响应不会用于渲染。后台刷新目录失败时保留已加载页面，并提供重试入口。

## 恢复边界

正式数据替换前校验候选目录，并备份旧展示目录。正常失败时恢复来源版本和展示目录。普通构建会拒绝实际子模块版本与成功同步记录错配的情况。

跨文件替换不承诺断电级事务。回退失败、清理失败或强制中断可能留下 `.data-sync/`。先确认没有任务运行，检查 `previous/` 备份、子模块提交与同步记录，恢复一致状态后再清理；不要盲目删除备份。

## 验收步骤

1. 启动 `npm run dev`，进入数据说明，确认只保留“手动同步”按钮。
2. 点击同步，成功后同步时间与检查栏一起刷新；旧的“发现更新”消失。
3. 保持服务运行，后台检查只刷新检查结果，不改变同步时间、子模块 HEAD 和代码资源。也可用 `npm run data:updates -- rpl` 验收单次检查。
4. 将间隔临时设为 1 分钟，等上次检查满 1 分钟加最多 15 秒调度延迟，观察自动检查；之后恢复 360。关闭 `enabled` 后不应继续调度，手动同步仍可运行。
5. 执行 `npm run build`、`npm test` 和浏览器验收。

测试在隔离 Git 仓库和候选目录中验证共用检查调用顺序、失败不拉取、拉取失败保留检查结果、检查固定版本、无变化同步及旧数据回退，不修改实际 RPL 子模块。

## CI 与回归

CI 预览使用 `RPL_AUTO_CHECK=0` 关闭真实远端定时检查，固定端口启动并等待就绪；调度与同步行为由隔离本地 Git 仓库验证。这样验收期间不会因真实远端变化改写同步记录。完整浏览器验收还覆盖异常接口响应、后台刷新失败保留页面及重试恢复。
